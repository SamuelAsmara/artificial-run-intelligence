# חלק 2 — הממצאים לפי חומרה

## 🔴 S1 — קטיעה שקטה ב-1000 שורות בלוח המאמן

**הכי חמור. פוגע בכל מסך המאמן.**

| מדד | מה שהמסך מראה | האמת במסד |
|---|---|---|
| אימונים השבוע | **32** | **80** |
| מתוכם בוצעו | 19 | 36 |
| אימונים ביום חמישי 20/8 | **8** (`3·3·1·1`) | **20** (`5·5·5·5`) |

**הסיבה** — `src/actions/coach.ts`, בתוך `getCoachWorkspace`:

```ts
const { data: workouts } = await supabase
  .from("plan_workouts")
  .select("plan_id, day_date, workout_type, planned_distance")
  .in("plan_id", planIds)
  .gte("day_date", windowFrom)
  .lte("day_date", windowTo)
```

אין `.range()`, אין `.limit()`, **ואין `order by`**. PostgREST מחזירה לכל היותר **1000 שורות**; בחלון של ±35 ימים ל-20 רצים יש כ-1,400. השאר נעלמות — ובלי `order by`, **לא מוגדר אילו** 1000 חוזרות.

**ההשלכה החמורה ביותר:** `Runner15-Coach1` פספס **2 אימונים השבוע** — יותר מכל אחד אחר — **והוא לא מופיע ברשימת "Needs you".** הרץ שהכי צריך את תשומת הלב של המאמן הוא זה שנופל מהרשימה.

**ועוד שתי שאילתות באותה פונקציה, על סף אותה תקלה:**

| שאילתה | שורות שנשלפות | שורות שבשימוש |
|---|---|---|
| `readiness_snapshots` | 2,162 (נחתך ל-1000) | 20 — האחרונה לכל רץ |
| `activities` | 1,105 (נחתך ל-1000) | 20 + סט ימים |

שתיהן **שורדות במקרה** — הן ממוינות יורד, אז השורה האחרונה לכל רץ נמצאת ב-1000 הראשונות. **ב-25 רצים זה יישבר.**

**התיקון המומלץ:** RPC אחת בפוסטגרס שמחזירה כבר מסוכם — ספירות ליום ולפי סוג מרוץ, ותמונת מצב אחרונה לכל רץ. סיבוב אחד, בלי תקרה, וקוד הלקוח נהיה קצר יותר. חלופה זולה יותר: לולאת `.range()` — עובדת, אבל מעבירה עדיין אלפי שורות לרשת כדי לספור אותן.

*(ובנוסף: `ids.map()` עם `.filter()` בפנים הוא 20 × 1,400 = 28,000 איטרציות בכל רינדור. ב-100 רצים זה 1.4 מיליון. `Map` לפי `plan_id` פותר.)*

## 🔴 S2 — `profiles.email` לא מסתנכרן אחרי שינוי מייל

הטריגר היחיד על `auth.users` הוא `on_auth_user_created` — **INSERT בלבד**. אחרי שרץ משנה מייל ומאשר, `auth.users.email` משתנה ו-`profiles.email` נשאר.

**ההשלכה:** רשימת הרצים אצל המאמן משתמשת ב-`full_name || email`. רץ בלי שם מלא יוצג לנצח בכתובת הישנה. וזה גם מקור אמת כפול שיסבך כל דוח עתידי.

**התיקון:** מיגרציה קצרה.

```sql
create or replace function public.sync_profile_email()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  update public.profiles set email = new.email where id = new.id;
  return new;
end $$;

create trigger on_auth_user_email_changed
  after update of email on auth.users
  for each row when (old.email is distinct from new.email)
  execute function public.sync_profile_email();
```

# חלק 3 — המלצות

## מסד נתונים

**1. RPC לסיכום לוח המאמן** — מטפל ב-S1 בשורש. במקום להעביר 3,000 שורות לדפדפן כדי לספור אותן, פוסטגרס מחזירה את הספירות. גם מהיר יותר וגם חסין לתקרות.

**2. טריגר סנכרון מייל** — S2. חמש שורות.

**3. `threshold_source` ו-`threshold_set_by`** — מה שהחלטנו: מאמן / אתלט / ספק / אין.

**4. `goal_races.target_time` — לחייב או להסיר.** כרגע הוא nullable, ריק אצל כולם, ושתי עמודות בממשק תלויות בו.

**5. אינדקסים — לבדוק אחרי S1.** `plan_workouts(plan_id, day_date)` קיים ומכסה את שאילתת הלוח. אחרי המעבר ל-RPC כדאי לוודא ב-`explain analyze` שהוא באמת בשימוש.

**6. `recovery_signals` מול `readiness_snapshots`** — 4,444 ו-4,760 שורות לאוכלוסייה של 40. ב-1,000 משתמשים זה 120 אלף ו-110 אלף בשנה. עדיין קטן, אבל שווה מדיניות שמירה מוגדרת לפני ולא אחרי.

## מה להוסיף

**1. פתיחת ריצה בודדת מכרטיס הרץ** (S6) — הפער היחיד שחוסם את "לרדת לרמת האימון הפרטני" שביקשת.

**2. הצגת עקבות עריכה** (S5) — "המאמן קיצר מ-10.0 ל-8.0 · הסיבה: העומס קפץ". הנתונים כבר במסד.

**3. הערה לאימון** — כרגע ה-Reminders הן "private to you". אין שום ערוץ שבו מאמן אומר משהו לרץ. זה הפער התפקודי הגדול ביותר במוצר.

**4. השוואה לביצועי עבר** — רציתי את זה במפורש לצד הרץ, וזה לא קיים. הנתונים כן קיימים: `best_efforts` ו-`pace_shape` נשמרים על כל ריצה ואף מסך לא קורא אותם. "הריצה הזו מול שלוש הריצות הדומות האחרונות שלך" היא תכונה שלמה שרוב הנתונים בשבילה כבר במקום.

## מה להוריד

**1. חמשת הספקים שאינם פעילים** — או להסתיר, או לסמן "בקרוב" במפורש.

**2. `recharts`** — עדיין ב-`package.json`, לא בשימוש.

**3. מסנן TARGET PACE** — עד שיהיה לו מקור, הוא מסנן על ריק.

## UX / UI

### לצד המאמן — לפי מה שתיארת

הבורד עצמו **טוב מאוד**. הכותרת (20 רצים · 4 מחזורים · 19/32 השבוע · המרוץ הבא בעוד 63 יום), "Worth knowing", ורשימת "Needs you" — זה בדיוק "תמונת מצב במבט על". והירידה לפרטים עובדת: רשימה מסוננת לפי מקצה ← כרטיס רץ ← עורך אימון.

מה שחסר כדי לסגור את מה שביקשת:

| שכבה | מצב |
|---|---|
| מבט על | ✅ קיים וטוב |
| רמת המקצה | 🟡 **חלקי** — יש מסנן לפי מקצה ברשימה, אבל **אין מסך של מקצה**: התוכנית של הקבוצה, ההתקדמות שלה, מי בתוכה מפגר |
| רמת הרץ | ✅ קיים |
| רמת האימון הבודד | ❌ **חסר** — אי אפשר לפתוח ריצה |

**"רמת המקצה" היא הפער האמיתי.** מאמן מנהל ארבעה מקצים; המערכת מציגה לו עשרים יחידים ומאפשרת לסנן. מסך מקצה — תוכנית הקבוצה, כמה מהקבוצה עומדים בה, מי חורג — הוא הדבר שהכי יקרב את המוצר לאיך שמאמן באמת חושב.

**ותקן קודם את S1.** בורד שמראה 32 במקום 80 הוא לא "תמונת מצב", הוא תמונה שגויה — וזה מסוכן יותר מלא להראות כלום.

### לצד הרץ

לא ראיתי אותו עם נתונים (אין לי סשן של רץ). מה שכן עולה מהמבנה:

- **מיקוד** — הרץ אמור לראות את עצמו מול התוכנית. זה קיים.
- **השוואה לעבר** — לא קיים, ומתבקש. ראה למעלה.
- **הגרף בלי צירים** — פוגע בשני הצדדים.

### כללי

- **ניווט כפול** (S5) — לתקן לפני כל הצגה. זה הדבר הראשון שכל מסתכל יראה
- **מספרים ריקים** — `—` בשתי עמודות אצל כל רץ מוריד אמון בכל השאר
- **`-0`** — פורמט

# מה שחוסם המשך בדיקה

כדי שאבדוק את **צד הרץ** צריך סשן של רץ. אני לא מזין סיסמאות, אז:

**התחבר פעם אחת ב-Chrome אחר (או פרופיל שני) כ-`runner2-coach1@demo.ari-coach.app`** והשאר את הלשונית פתוחה. אז אוכל לסרוק את הדשבורד, מסך הריצות, ריצה בודדת ומסך התוכנית מצד הרץ, ולסגור את החלק החסר בדוח.

Runner2 הוא הבחירה הנכונה: הוא מעלה נפח מהר מדי, יש לו אימון שפוספס השבוע, ויש לו שני אימונים שהמאמן קיצר — כלומר הוא מפעיל את רוב מקרי הקצה במסך אחד.
